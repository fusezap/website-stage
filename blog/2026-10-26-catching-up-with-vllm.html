Catching up with vLLM,
then a chip that isn’t a GPU

Right first, then fast. How we closed the gap on NVIDIA, row by row, and what happened the first time our kernels met a chip that isn’t a GPU.

26 October 2026 · Updated 6 November · The FuseZap team

On 20 October we put FuseZap next to vLLM on one NVIDIA H100. The answers were right. The speed wasn’t. vLLM was faster, and the gap grew as more people asked at once. If you’ve ever watched your own chip lose a table to a name everyone knows, you know that feeling.

This month FuseZap went from well behind vLLM to level with it on one NVIDIA GPU, and to within a few percent on 70B models across two. On the same day we ran our kernels on a real AWS Inferentia2 for the first time. We decided early that FuseZap would be right before it was fast, so every number here was checked against a full-precision reference first. This is what was slow, what we changed, and what still isn’t done.

Where we started

Every speed story starts with an honest baseline. Ours wasn’t flattering.

We measure ourselves against vLLM 0.32, the open-source engine most teams already trust. On 20 October we ran both engines on the same H100 with a 7B model.

FuseZap was right, but slow. It ran at 70% of vLLM’s speed for one person and 53% with 32 people at once. That run used longer prompts than the ones below (512 tokens in rather than 128), so read it as where we started, not as a like-for-like comparison. The full table is on the engineering page.

What was slow, and what we changed

Then came the part nobody outside sees: finding where the time actually went.

Most of the gap was in two places. The matrix multiplies that run for every new token were slow. And our server and engine shared one Python process, so they waited on each other.

We fixed both, then rewrote the attention step. Then we ran it all again.

On 26 October we ran the two engines again, back to back on the same machine. FuseZap now gets 99–105% of vLLM’s per-token speed and the same time to the first token.

Speed only counts if the answers are still right. On this model FuseZap picks the same next token as a full-precision reference 99.6% of the time. vLLM, on the same test, does 99.3%.

70B across two GPUs, and the NCCL surprise

Bigger models told a similar story. Our first 70B runs across two H200s, on 25 October, came in at about 70% of vLLM.

We traced it to the step where the two GPUs add up their results. Inside a CUDA graph, NVIDIA’s NCCL library took about seven times as long for that step as it does outside one. Seven times longer, for the same work. We wrote our own one-kernel version.

Now we’re at 96–101% of vLLM per token.

vLLM is still quicker to the first token on two GPUs: 45–66 ms for us against about 34–36 ms. That’s what we’re working on now.

The answers held up. On Llama-3.3-70B, FuseZap picks the same next token as the full-precision reference 99.93% of the time (vLLM: 99.61%). Serving Qwen2.5-72B, it gets the same results as vLLM on all 151 tool-call and JSON tasks.

Then a chip that isn’t a GPU

This is the part closest to your world.

Everything above runs on NVIDIA. The real test is a chip FuseZap wasn’t built around, so we picked AWS Inferentia2.

We wrote one new Core backend for it: a renderer that turns our kernels into AWS’s NKI kernel language, and a device that compiles each kernel once and keeps it loaded on the chip. Serve, the models and the API didn’t change.

On 26 October we ran it on a real Inferentia2 for the first time, on one AWS inf2.xlarge machine. Of the operation tests that run on the chip, 1,171 of 1,174 passed. The 3 that failed are float32 precision in exp2 and tanh, where the chip’s built-in approximations are a little less precise than our tests allow. We’re fixing them.

Our matrix-multiply and attention kernels passed all 81 of their tests on the chip. A kernel that’s already loaded launches in about 160–170 microseconds.

We also found a bug: log2 gives wrong answers for some inputs, and we’re fixing that too. Every test count and timing is in the Inferentia2 notes.

A day later we served our first model on it. Qwen2.5-0.5B, the small model we always start with, answered all 24 of our reference prompts on the real chip, and every one of the 1,441 tokens matched the full-precision reference. It’s slow for now, about 161 milliseconds a token, because each token takes 245 separate kernel launches. That number is the thing we’re working on next. We fixed the exp2, tanh and log2 problems from the day before, too.

Slow, but right, every token of it. If you’ve waited for a first token from new silicon, you know which of those matters first.

Update, 31 October. On 29 October FuseZap served Qwen2.5-7B, split across both cores of one Inferentia2 (an AWS inf2.8xlarge), behind the same OpenAI API. Checked with FuseZap Validate, it takes 38.6 milliseconds a token, against 40.6 for AWS’s own library, NxD Inference, on the same kind of machine. With four users at once it writes 96.9 tokens a second, against 81.7. AWS’s library is still quicker to the first token, and that’s what we’re working on now. The details are in the Inferentia2 notes.

Update, 2 November. We rewrote the kernels that process the prompt, and the first token on Inferentia2 now takes 55 milliseconds, down from 91, against 51 for AWS’s library. The answers are exactly the same as before, bit for bit.

What’s still not done

You’d find the gaps the first time you ran our numbers against your own. Better that you hear them from us.

  • On two GPUs, vLLM is still quicker to the first token (above).
  • FP8 speed and longer prompts haven’t been re-measured since 20 October.
  • On Inferentia2, AWS’s own library is still slightly quicker to the first token, by about 5 ms.

We’ll write again when the first token on Inferentia2 is level.

How we measured

Lower is faster in both tables. “How close” is vLLM’s time divided by ours, so above 100% means FuseZap is faster.

Every run is FuseZap Validate’s short chat workload: each request reads 128 tokens and writes 128, three repetitions per load, against vLLM 0.32.0. On the H100 both engines ran back to back on one machine on 26 October.

The two-GPU runs were on separate 2× H200 machines a day apart (vLLM on 25 October, FuseZap on 26 October), not back to back on one, so read a few percent either way as noise.

On NVIDIA, matrix multiply, attention, the all-reduce between GPUs and a few other hot spots use hand-written CUDA kernels, large prompt-processing matrix multiplies call NVIDIA’s cuBLASLt, and NCCL carries the larger GPU-to-GPU transfers; the rest is generated.

Every setting and number is on the engineering page, so you can check our work.

The last row

The row we think about most is the last one. Your chip.

The Inferentia2 row above it started where your chip may be today. Tests on a simulator. Then a first full run, with three failures to chase. Then a first model, slow and right. Then a bigger one, measured against the chip maker’s own library.

None of that needed a new server or new models. It needed one backend, and the patience to check the answers before counting the milliseconds.

So here’s a question to take to your next team meeting. Which model would you most like to see answer correctly on your silicon first, and what would your simulator need to run it?
