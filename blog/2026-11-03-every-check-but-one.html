Every check
but one.

In October, a popular open 70B model passed Validate on accuracy, on every functional check and on every reliability check. Then it got BLOCK, for sending numbers as text. Why one red gate was the right call, and why your next driver release is the same bet.

3 November 2026 · The FuseZap team

The wordBLOCKdon’t ship this release

You’re the one who signs off the release. The report is open. Accuracy against the reference: pass. Functional checks: nine of nine. Reliability, the overload, cancel and restart checks: eight of eight. JSON output: 50 of 50 valid.

Twenty-one gates green. One red. And one word at the top of the page: BLOCK.

That run is real. We ran FuseZap Validate in October against vLLM serving a popular open 70B model across two NVIDIA H200s. We’re not naming the model, because this post isn’t about the model. It’s about the seat you’re sitting in when a report like that lands, and what you do next.

What the red gate said

The failed gate was tool calls. Validate gives the model tasks that need a tool, the way an agent would, and checks each call: the right tool, or none when none is needed, and arguments that match the tool’s schema and the expected values.

The bar is 90%. The model got 51 of 93 right.

Most of the failures had the same cause. It sent numbers and true/false values as text, where the tool expected a number or a boolean. The report names each one. A few, exactly as it logged them:

  • A refund of 49.99, sent as the text "49.99".
  • A thermostat set to "68".
  • A feature flag switched to "false".

Read that last one twice. In Python and in JavaScript, any non-empty string counts as true. Code that doesn’t check its types would read "false" and turn the flag on.

The whole run took about eight and a half minutes.

Why this is the failure customers find

A wrong word in a chat answer gets read by a person. They notice, they frown, they ask again.

A tool call gets read by code. Nobody looks at it. An agent calls the refund tool, and either the payments service rejects the amount, or a forgiving parser quietly converts it and the problem moves somewhere harder to see. Either way, the first person to find out is usually your customer, reading someone else’s logs.

And nothing else in that report would have warned you. The model’s answers matched the reference. The server held up under overload and came back cleanly after a restart. Its JSON output was valid every time. By most of the numbers people compare, this was a good release.

It just couldn’t be trusted with a tool.

Same server, another model, another word

On the same vLLM, on the same two H200s, we ran Qwen2.5-72B. It passed every gate that ran: 22 passed, none failed. Its tool calls were right 98.92% of the time. The word was PROMOTE. That run is our sample report, exactly as Validate wrote it.

There’s one more line in the blocked model’s report worth knowing. By default, the server checked the shape of each call, the tool’s name and valid JSON, but not the types inside it unless a tool was marked strict. With strict tools turned on, the same model got 77 of 81 calls right.

So the answer might be a setting, not a different model. Validate doesn’t make that choice for you. It makes sure you make it before your customers do.

How Validate decides

Validate calls your OpenAI-compatible server the way your customers do, on your own systems. It never calls home. It runs six kinds of checks:

  • Answers, token by token, against a full-precision reference.
  • Tool calls and JSON: 101 tool-call tasks and 50 JSON tasks, with each failure named.
  • Long prompts of up to 32,768 tokens, with a fact hidden inside.
  • Speed, at the loads you choose, with confidence intervals.
  • Under pressure: overload, cancelled requests, abandoned connections and a restart.
  • Against last time: everything compared with the stored report of the release you approved.

Rates like tool-call validity are judged on a 95% confidence interval, and a pass needs the whole interval to clear the bar. For 51 of 93, the interval ran from about 45% to 65%. Nowhere near 90. So, BLOCK: a check failed on valid data.

Gates that can’t run are skipped, never quietly passed, and the report says why. The Qwen2.5-72B run skipped 12: seven compare with an earlier approved release, and that run had none.

When the interval straddles the bar, the word is REVIEW, and a person decides. A word you can trust has to be able to say “I don’t know.”

Every run leaves the same evidence for everyone: the word for the release manager, the gates for the engineers, an HTML and PDF summary, the raw JSON and CSVs, and an exit code your CI already understands. The rules behind each verdict are on the method page.

Your release night is the same bet

If you build a chip, you’ve had this night, from the other side.

A new driver lands. The compiler moves. A kernel library gets faster. Someone wants a new model running by Friday. Each change is a small bet that nothing a customer depends on has moved. Most weeks, nothing has. The weeks it has, you want to be the first to know.

On a chip, what changes is usually below the model, not the model itself. We’ve seen how small those changes can be. On Inferentia2, the chip’s built-in exp2 and tanh were a little less precise than our tests allow. A difference like that won’t show up as a crash. If it shows up at all, it’s a slightly different answer, a token here and there. You want a check that notices before an agent does.

That’s why Validate compares every release twice: against a full-precision reference, so you see drift and not just pass or fail, and against the release you approved last time.

Here’s a question to take to your next release review. If your next compiler release changed how one model calls its tools, which of your tests would fail? And who would see it first: your team, or your customer’s agent?
