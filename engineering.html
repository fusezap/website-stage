We wrote this page for engineers who want the detail behind the home page. It covers what FuseZap is and how we measured it, including what isn’t done yet. FuseZap has two products: Validate, our licensed release checker, and Core and Serve, the engine and server, which are open source (Apache-2.0), release coming. Most of this page is about how Core and Serve work and how we measured them; how Validate decides is under Sample Validate report. For the story behind the October speed numbers, in plainer words, read our blog post. If something here doesn’t match what you see when we work together, tell us.

What FuseZap is

In plain terms first. FuseZap Core is our compiler and engine, and FuseZap Serve is the server on top of it. Both are ordinary software: they run as a process on the operating system and your chip’s driver, like any other server. They aren’t firmware and they aren’t part of the OS.

FuseZap Core is a compiler and engine for LLM inference. A model is expressed in 28 primitive operations. The compiler schedules and fuses them into kernels, generates source for the target, and tunes launch parameters with a beam search. The serving layer runs on top of whatever the compiler produces.

Porting to a new chip means writing one backend. A backend has four parts:

  • Renderer: turns our kernel IR into source in your kernel language (today a C dialect such as C, Metal or CUDA, or a Python tile language such as Inferentia’s NKI; LLVM- or MLIR-level entry points are possible but not built yet).
  • Compiler hook: calls your toolchain to build that source into something your chip runs. Builds are cached on disk.
  • Runtime: loads kernels and launches them through your driver API.
  • Allocator: device memory through your driver.

The backend only needs a way to compile a kernel and a way to launch it, so a functional simulator with the same interface should work before silicon exists. That’s how we built our AWS Inferentia2 backend: on AWS’s simulator first, then on the real chip, where almost every test passed on the first full run (details below). On a simulator we prove correctness; performance tuning waits for real hardware.

Four parts get a chip running correctly. Making it fast takes more. On NVIDIA that means hand-written CUDA for matrix multiply, attention, normalisation and token selection, and, across GPUs, an all-reduce fused with the normalisation after it (the same one-kernel approach as vLLM’s custom all-reduce), all plugged in through the custom-kernel hook. Large prompt-processing matrix multiplies call NVIDIA’s cuBLASLt library, used only after a start-up self-check shows its results don’t depend on batch size, and NCCL carries the larger GPU-to-GPU transfers. We expect every chip to need a handful of tuned kernels like these, ideally ones its maker already has.

Tuned kernels you already have, such as matmul or attention, plug in through a custom-kernel hook and are called directly instead of generated. The hook recognises matrix multiply and attention today, and so far it has carried our own kernels and NVIDIA’s cuBLASLt, not yet a chip maker’s. Everything above the backend is shared by every chip: the compiler passes, the model code, the serving engine and the tests.

Why not a vLLM plugin?

It’s a fair question, and for some teams a plugin is the right answer. vLLM describes itself as running any model on any hardware, and its hardware support is real, but in practice each chip it supports builds on its maker’s own PyTorch or JAX backend and hand-tuned kernels. vLLM’s hardware plugin interface gives you its scheduler, batching and API. What it doesn’t give you is the kernels. Your team still writes and tunes kernels for the operations each model uses, and every time a model introduces a new attention variant, activation or quantization format, that work starts again. You also follow vLLM’s internals, which change often.

FuseZap works one level lower. Models are built from 28 primitive operations, and the compiler fuses and generates kernels for your chip from those, tuning them with a beam search. A new model is mostly a new combination of the same primitives, so it should need little or no new kernel work. Your tuned matmul and attention kernels still plug in where they’re faster.

That is a claim we intend to prove, not just make. On our first non-GPU accelerator (AWS Inferentia2, now serving a 7B model on the real chip) we’re recording how much backend code, time and money the first model takes, and then the second. We’ll publish both numbers here.

Hardware capability contract (v0)

Before we start on a chip, we want to know whether it can host a backend at all. This is the list we check it against.

This is what a chip needs to offer for a FuseZap backend. It is a first version; the Inferentia2 port is testing it now, and we’ll version it as it changes.

CapabilityNeededDetails
CompileRequiredTurn generated kernel source (a C dialect or a Python tile language today; LLVM IR or MLIR later) into something a host process can load, at runtime or ahead of time.
Launch and waitRequiredLaunch a kernel with buffer addresses and integer arguments, wait for it to finish, and time it.
MemoryRequiredAllocate and free device buffers, and copy between host and device.
Data typesRequired: float32, int32float16 or bfloat16 for useful speed; int8 for quantized weights; FP8 where the hardware has it.
OperationsRequiredElementwise arithmetic and comparisons, exp2, log2, sqrt and sin, and sum and max along an axis. Integer division and modulo are used for indexing; emulating them on chips without them isn’t built yet.
Tuned kernelsOptionalYour matmul and attention kernels, called through our custom-kernel hook instead of generated ones.
Scratchpad and barriersOptionalOn-chip memory and synchronization, used by the generated kernels when available.
Memory hierarchyFlat device memory todayGenerated kernels assume device memory plus optional on-chip shared memory, as on GPUs. Software-managed scratchpads with explicit DMA and double buffering are being built for Inferentia2 now; we’ll publish what changed.
Multiple devicesOptionalFor models larger than one chip. Tensor parallelism runs on NVIDIA and AWS Inferentia2 today (fusezap serve --tp N, tested with two GPUs and with the two NeuronCores of one Inferentia2). On another chip it needs a way to sum a buffer across devices: a collective library, or peer memory access plus a barrier. Pipeline parallelism isn’t built.

Real chips don’t always fit a clean interface. Inferentia2 already breaks a few of these assumptions: shapes are fixed when a kernel is compiled, its kernel language works on whole tiles rather than threads, and its compiler has to run in a separate process. We’ll publish every exception we hit, along with how we handled it.

Correctness method

We decided to be right before being fast, so this is the part we spend the most time on. Here is how we check that FuseZap gives the same answers as the reference.

  • Operations: every primitive and composed op is tested against NumPy and PyTorch on four execution tiers (a pure-Python interpreter, NumPy, compiled CPU and Metal).
  • Training parity: a small GPT trains with losses matching PyTorch within 1e-4 on every tier.
  • Models: Qwen2.5-0.5B-Instruct produces 64 greedy tokens identical to Hugging Face Transformers at FP32. Chat templates match Hugging Face for six tokenizers (Qwen2.5, Llama 3.0 to 3.2, Mistral and SmolLM2). Real weights tested end to end so far: Qwen2.5 0.5B, 7B, 32B and 72B, and Llama-3.3-70B. Mistral uses the same model code but hasn’t been run with real weights yet.
  • 7B on NVIDIA: Qwen2.5-7B-Instruct in bf16 on an H100 picks the same next token as the Hugging Face FP32 reference at 99.3% of 1,024 positions (our bar is 99%, and Hugging Face’s own bf16 scores 99.1%).
  • 70B across two GPUs: served with tensor parallelism on two H200s in bf16, measured by FuseZap Validate against float32 references: Llama-3.3-70B-Instruct 99.93% top-1 agreement (vLLM 0.32 on the same test: 99.61%), Qwen2.5-72B-Instruct 99.33% (vLLM: 99.02%).
  • Tool calls and JSON: on Qwen2.5-72B, FuseZap and vLLM give the same result on every one of Validate’s 101 tool-call and 50 JSON tasks, in every mode: tool calls 92 of 93 with automatic tool choice, 81 of 81 with a named tool, 78 of 81 with strict tools; JSON 50 of 50 with a schema, in JSON mode and from the prompt alone.
  • Batching: 32 concurrent requests each produce tokens bit-identical to running alone, including under chunked prefill and preemption.
  • API: the server is exercised with OpenAI’s official Python client, including streaming and concurrent streams. Tool calls are parsed in the Hermes, Mistral and Llama 3.1+ formats; JSON-schema output and strict tools use grammar-constrained decoding (llguidance); logprobs are returned.

Getting here took two fixes worth knowing about if you build a multi-chip backend. Small all-reduces inside CUDA graphs were slow through NCCL, so a one-kernel all-reduce, fused with the normalisation that follows it, now handles them. And weight loading no longer keeps a host copy of every weight after uploading it (that was about 60 GB per GPU on this model), so host memory stays bounded.

First run on a chip that isn’t a GPU: AWS Inferentia2 (26–29 October 2026)

Everything above is NVIDIA. We wanted to know whether the “one new backend per chip” idea holds on a chip FuseZap wasn’t built around. So we brought up AWS Inferentia2: first on AWS’s simulator, then on the real chip. On 26 October it ran our operations and kernels correctly, with a few exceptions listed below. On 27 October it served its first model (below), and on 29 October a 7B model across both of the chip’s cores, measured against AWS’s own library (below).

What we built is one new Core backend. Its renderer turns our kernel IR into AWS’s NKI kernel language. Its device compiles each kernel once with AWS’s neuronx-cc compiler, caches the result on disk, loads it once into a long-lived runtime process and launches it on buffers that stay on the chip. Serve, the model code and the API are unchanged above it.

Setup: one AWS inf2.xlarge (one Inferentia2 device with two NeuronCores and 32 GB of device memory), AWS’s Deep Learning AMI with Neuron SDK 2.33, nki 0.6.0, neuronx-cc 2.27 and the nrtpy 2.35 runtime. The whole run took 22 minutes.

The last launch row is why the device works the way it does. Our first run, earlier the same day, used nki.jit, which compiles and loads the kernel again on every call: about 1.3 seconds each, whatever the size. Compiling once and keeping the kernel loaded brought a launch down to about 160–170 microseconds. Most of that is still on the host side, and a model runs many kernels per token, so launch overhead is the first thing we’ll work on for speed.

  • Then speed, starting with fewer kernel launches per token: fused kernels, or launches batched inside the runtime process.
  • No speed comparison with AWS’s own software yet. We’ll publish one when a model serves. Done on 29 October (below).
  • The exp2, tanh and log2 fixes above. Done on 27 October.
  • Our larger matrix-multiply and attention check at Qwen model shapes didn’t run in this session, because of a bug in our test script. In the earlier run its first 6 cases passed on the chip. On 27 October all 8 cases passed.
  • How much backend code and time the first and the second model take. We’ll publish both numbers, as promised above.

The only edit is that the validator machine’s container name is removed. It covers accuracy against a float32 reference, nine functional checks, tool calls and JSON, speed at three loads, a stability run and eight reliability checks. It was a single-release run, so the comparison against an approved release is listed as skipped.

How Validate decides: every gate passes, fails, or is too close to call. Rates such as tool-call validity are judged on 95% Wilson intervals, so a pass needs the whole interval to clear the bar. The run ends with a decision, PROMOTE (every gate passed), BLOCK (a gate failed) or REVIEW (too close to call, or something couldn’t run: a person decides), and an exit code of 0, 1, 2 or 3 for CI. Structured-output failures are sorted into 14 error types, from a missing tool call to a wrong argument type, with the exact argument path. Besides the built-in tasks (101 tool-call tasks in 12 categories, 50 JSON tasks in 7), you can add your own tool and JSON task files. Long-context checks hide a fact in prompts of 4k to 32k tokens and judge each length separately; mixed workloads run 512- and 4,096-token prompts together. Evidence comes as JUnit, JSON, CSV, HTML and PDF. A candidate can be compared with a stored report of the release you approved, so the old release doesn’t need to stay running.

What isn’t done yet

We’d rather you hear this from us than find it yourself.

  • Beyond NVIDIA and Apple, only one accelerator serves models so far. Today: CPU (as a correctness reference), Apple Metal, NVIDIA CUDA and AWS Inferentia2, which serves Qwen2.5-7B across both cores of one chip, a little faster per token than AWS’s own library and slightly slower to the first token (above). AMD HIP follows.
  • Nothing is available to download yet. Core and Serve are open source (Apache-2.0), release coming; the code isn’t public yet. Validate, the licensed product, runs as one command in CI today, and we’re finishing licensing (offline, signed licence files) before handing it out; until then, early access is hands-on, with us.
  • Only Qwen2.5 and Llama 3.3 weights have been tested end to end. Mixture-of-experts and sliding-window attention aren’t supported yet.
  • Across two GPUs, still slower than vLLM to the first token: 44.8 ms against 34.0 ms (Llama-3.3-70B) and 65.9 against 36.0 ms (Qwen2.5-72B) for one request. On one GPU it’s level. FP8 speed and longer prompts haven’t been re-measured since 20 October.
  • Multi-device: tensor parallelism is tested on two NVIDIA GPUs (two H200s, and two RTX 4090s for small models) and on the two NeuronCores of one Inferentia2. There’s no pipeline parallelism.
  • No prefix caching. A streamed request that asks for logprobs, or uses Hermes or Mistral tool calls, gets its reply when generation finishes rather than token by token. Presence and frequency penalties and logit bias are ignored.
  • FP8 runs natively on NVIDIA H100 (weights and activations); on other backends it is weight-only.
