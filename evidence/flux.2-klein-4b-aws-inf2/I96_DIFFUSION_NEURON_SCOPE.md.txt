# I96: FLUX.2 [klein] 4B on the NEURON backend (Inferentia2, Trainium1): scope

Date: 2026-11-04. Branch `i96-diffusion-neuron-scope` (from `diff-merge` 2cfc420). Desk work only: no AWS, RunPod or
GPU job ran. Evidence: the code (cited file:line) and a new probe, `scripts/i96_probe.py`, run on the Mac (NKISHIM tier).

## 0. Summary

- The klein transformer already lowers on NEURON. Nothing in one 1024² step fails to render. The probe found 665
  kernel launches per step in float32, 164 of them distinct, and 0 failures.
- Three things are slow or heavy today, and each is a small model-side change:
  1. In bf16, attention misses the flash kernel and builds the full 4608 × 4608 score matrix (1.9 GiB per head set).
  2. In bf16, every linear casts its weight to a float32 copy first, then runs the float32 matmul.
  3. In float32, the two output projections of each double block miss the matmul pattern and run as a VectorE GEMM.
- The Qwen3 text encoder does not run on NEURON. `Llama` refuses q/k RMSNorm on a NEURON tier.
- The VAE lowers, but at 1024² its im2col buffers reach 9 GiB. It should run on the host CPU first.
- A first chip run within ~<redacted> on inf2 and ~<redacted> on trn1 is realistic **only if** the NEFFs are compiled on a cheap
  CPU pod first. The biggest unknown is compile time: one step has kernels with up to 46,656 unrolled `nc_matmul`s.
- The first run should prove one thing: the transformer's velocity at each of the 4 steps, teacher-forced, against
  the float32 reference that already exists on the Mac. Not a fast image.

## 1. How NEURON runs a model today (verified from code)

There are two layers. klein can only use the first.

1. **Generic lowering of the lazy graph.** Any Tensor graph is scheduled as usual. Each kernel is rendered by
   `fusezap/codegen/nki.py` (elementwise and reduce ops on VectorE / ScalarE / GpSimd; supported ops and limits at
   nki.py:16-34). The scheduler hook turns two patterns into hand-written TensorE kernels:
   `matmul` and `attention` / `attention_mask` (offered at fusezap/device/neuron.py:706-710; rendered by
   `nki_kernels.render_matmul` nki_kernels.py:76 and `render_attention` :185). Each kernel is one NEFF, compiled once
   per (source, sizes) and cached on disk (neuron.py:164-236). Eager code launches one NEFF per schedule item. Under
   `fz.jit`, `fuse_schedule` can merge items between fences into one NEFF (neuron.py:842).
   A kernel the renderer cannot lower raises `NKIUnsupported`; nothing falls back to another device (neuron.py:33).
2. **Hand-written per-model kernels.** Llama-family decode uses its own NKI kernels: a whole decoder layer as one
   kernel (`LayerSpec`, nki_kernels.py:723, `render_layer` :1003), the head (`HeadSpec` :539), RMSNorm, the KV write,
   bf16 variants (`fusezap/codegen/nki_bf16.py`). `Llama` picks them itself (llama.py:303-313, :354-360,
   fusezap/serve/neuron_kv.py). Qwen2.5-0.5B/7B and Llama-3.1-8B reached their speed through these. None of them
   apply to the FLUX.2 transformer or the VAE.

Two limits matter for klein:
- The matmul and attention patterns accept **float32 only** (fusezap/schedule.py:386, :388, :450, :495;
  nki_kernels.py:22).
- A pattern operand must be **one plain strided view** (`_sview`, schedule.py:362-367). A permuted-then-reshaped
  tensor is two views, so it is not matched.

## 2. Each piece of the klein pipeline on NEURON

Probe: `PYTHONPATH=. python scripts/i96_probe.py`. Part A builds each piece at klein's real 1024² shapes (4096 image
+ 512 text tokens = 4608) over unallocated device buffers, schedules it, and renders every item as NEURONDevice
would. Part B runs tiny models on NKISHIM (the numpy model of nki 0.6) against CPU. Run on the Mac: under 2 minutes,
almost no memory. "Renders" means the NKI source is produced. It does not yet mean neuronx-cc compiles it (that
needs Linux x86_64; work item W4).

**Transformer (fusezap/serve/models/flux2.py), one 1024² step:**

| Piece | Code | float32 today | bf16 today |
|---|---|---|---|
| Timestep embedding (sin/cos, 2 linears) + 3 shared modulations | flux2.py:227-251 | Runs: TensorE matmul + generic kernels (SIN has range reduction, nki.py:565) | Runs, plus weight casts |
| x / context embedders | flux2.py:253-254 | Runs (TensorE) | Runs, plus casts |
| LayerNorm + modulate (adaLN) | flux2.py:160, :194 | Runs (generic, 3 kernels) | Runs |
| q/k/v and FF linears | flux2.py:159, :196, :208 | Runs (TensorE `fz_matmul`) | Runs, but each weight is first cast to a float32 copy, then the float32 matmul (TensorE at 1/4 rate) |
| Output projections `to_out.0` / `to_add_out` on the attention output | flux2.py:183-184, :204-205 | **Falls back** to a VectorE GEMM (10 per step): the input is a permute view, so `_sview` rejects it. A `.contiguous()` fixes it (checked) | Matched (the cast makes it contiguous) |
| Per-head q/k RMSNorm | flux2.py:161-164 | Runs (generic) | Runs |

Cause: `sdpa` casts to float32 only on METAL (flux2.py:92) |
| SwiGLU | flux2.py:165-167 | Runs (generic) | Runs |
| Single block (fused qkv+MLP-in, 3072 → 27648) | flux2.py:214-225 | Runs | Runs, plus casts |
| Output norm + `proj_out` | flux2.py:262-264 | Runs | Runs |
| **Whole step** (5 double + 20 single blocks) | flux2.py:244-264 | **665 launches, 164 distinct kernels, 124 TensorE, 10 VectorE GEMMs, 0 failures** | **940 launches, 185 distinct, no flash attention, 0 failures** |

**VAE decoder (fusezap/serve/models/flux2_vae.py) at 1024²:**

| Piece | Code | NEURON today |
|---|---|---|
| conv2d 3×3 and 1×1 | flux2_vae.py:97 → tensor.py:746-786 | Runs as im2col (8 copy kernels) + one TensorE matmul. | BN denormalize + unpatchify | flux2_vae.py:136-145 | Runs (1 kernel) |

**Text encoder (fusezap/serve/models/text_encoder.py):** **missing on NEURON.** It is a `Llama` with a Qwen3 config,
and `Llama.__init__` raises `NotImplementedError("q/k RMSNorm (Qwen3) is not in the NEURON kernels yet")` on any
NEURON tier (llama.py:223-224). The probe confirms it on NKISHIM. The Llama NEURON path is also built for decode with
a KV cache; `encode()` (hidden states 9/18/27 over 512 tokens) has never run there.

**Tiny numerics on NKISHIM vs CPU (probe part B):** transformer float32 max rel err 6.0e-7; bf16 1.9e-3 (vs CPU bf16);
VAE float32 1.6e-6. So the generic lowering computes the right thing at small shapes. Real shapes are W2.

## 4b. Done on the Mac (2026-11-04/05): W1, W2, W3, W6

All free. No AWS, RunPod or GPU job ran.

**W1, routing (fusezap/serve/models/flux2.py).** Each change applies only on a NEURON tier (NEURON, NKISHIM, NKISIM).
METAL and CPU take the same code paths as before.
- `sdpa` casts bf16 q/k/v to float32 on NEURON as it does on METAL, so the flash kernel takes klein's attention.
- `_attn` makes the attention output contiguous on NEURON, so `to_out` / `to_add_out` reach the TensorE matmul.
- With bf16 weights on NEURON, every 2-D weight is stored K-major (relaid on the host at load) and `_lin` calls
  `neuron_kv.matmul_bf16` (bf16 operands, float32 accumulation). No float32 weight copy is made.
  `FZ_KLEIN_NEURON_BF16MM=0` turns this off.
- Probe after W1 (docs/diff/i96_probe.txt), one 1024² step: float32 has 660 launches, 0 VectorE GEMMs (10 before).
  bf16 has 726 launches, 0 VectorE GEMMs, flash attention in every block, and MatmulBF16 for every linear. Before W1,
  bf16 had 940 launches, no flash attention and a float32 copy of each weight.
- Tests: the diffusion test files on the default tiers (interp, NPY, CPU, METAL) give 50 passed. The same files on
  NKISHIM give 21 passed. The new `tests/test_flux2_neuron.py` gives 5 passed: tiny model in f32 and bf16 vs CPU,
  kernel routing checks, and a check that METAL/CPU are untouched.
- METAL bf16, 512², prompt 0, with real weights (`scripts/i96_klein_chip.py --device METAL`): G3 worst 4.6e-2 and G4 5.1e-2,
  against bars of 0.151 and 0.309.

## 5. Is a first chip run possible within ~<redacted> (inf2) and ~<redacted> (trn1)?

Yes, with conditions. Prices from docs/aws_spend.csv: inf2.8xlarge ~<redacted>, trn1.2xlarge ~<redacted>. So <redacted> is ~7 h
and <redacted> is ~3.7 h.

What one attempt costs, if W4's NEFFs are ready:
- Boot, setup, host check: ~15 min (past jobs). Transformer download: 7.2 GB, a few minutes.
- Loading 185 cached NEFFs and 7.2 GiB of weights: minutes.
- Compute: one step is ~42 TFLOP (I82 §3). Today every matmul is float32 on TensorE (23 TFLOPS per core, 1/4 of
  bf16), so the floor is ~1.8 s per step. Real efficiency is unmeasured; 10-60 s per step is a guess [est].
  2 prompts × 4 teacher-forced steps × 2 sizes plus 1 free run: well under 30 min even at the slow end.
- One attempt: about 1 h, about <redacted> on inf2 and <redacted> on trn1. <redacted> covers ~5 attempts; <redacted> covers ~2-3.

What breaks the budget:
- **Compiling on the chip instance.** 164-185 distinct kernels, some with tens of thousands of unrolled matmuls.
  Past fused Llama kernels took ~200 s each cold. The klein ones are bigger. Compile time is unknown. If it is
  minutes per kernel, compiling on the instance could take hours. So W4 must come first, on a CPU pod.
- NEFF pins. The cache key includes the compiler versions and the target (neuron.py:164, :187). The pod must use the
  instance's exact nki / neuronx-cc pins, and trn1 needs its own NEFF set.
- An HBM surprise (NEFF code size). W3 and W4 bound it.

What the first run would prove:
- The klein transformer runs on a NeuronCore through FuseZap's generic lowering, with no klein-specific kernel.
- Its velocities match the float32 reference within the bf16 bar at 512² and 1024² (G3), and a 4-step free run
  stays close (G4).
- Measured s/step, launches per step, peak HBM and compile cost. These set the speed work.

What it would not prove: speed (float32 TensorE, eager, ~665 launches per step), the text encoder on chip, or the VAE
on chip. A full image would come from host-CPU encoder and VAE around the chip's transformer.
