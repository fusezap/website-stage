One monthly train

A release you can plan a Friday around.

You have a launch to protect. So our releases should be boring in the best way: predictable, tested together, and never a surprise.

A FuseZap release such as “FuseZap 0.3” is Core 0.3 and Validate 0.3, tested together and released on the same day. Until version 1.0 we plan a new minor release each month.

Nothing here is a download yet. This is how it will work.

The rules

Three kinds of release.

Every version number tells you what kind of change it is, and what it can’t contain.

  • 0.3.0rc1Pre-releaseTo try before the minor lands.
  • 0.3Minor, monthlyCore and Validate together, same day.
  • 0.3.1Patch, when neededFixes only. Nothing removed.
  • 01PatchesPatch releases, such as 0.3.1, ship when they’re needed and can ship for one product alone. A patch is for wrong output, a crash or hang, a security issue, a speed regression of more than 5% on a Supported chip, or support for a new model that needs no API change. Nothing is removed in a patch.
  • 02VersionsVersions follow semantic versioning, staying at 0.y.z until the server API and the backend porting API are frozen; that’s 1.0. Pre-releases look like 0.3.0rc1. The latest minor and the one before it get fixes.
  • 03Retiring thingsAnything we retire gets a warning first, then goes off by default, then is removed, at least two minors later. That covers settings, command-line flags, the HTTP API, the Validate report format and its exit codes.
01Release notesEvery release

Everything you’d want to know before you upgrade.

Including the parts that are awkward to write.

Known issues get a workaround and a target release, not silence. And every note says what happened to the last note’s “next” items.

  1. Highlights, then new chips and models.
  2. The support matrix for that release: chips × models × status, each cell with its evidence and the versions it was tested with.
  3. Performance: every number with its baseline, hardware, commit and the command to reproduce it.
  4. Fixes, breaking changes, deprecations and security.
  5. Known issues, each with a workaround and a target release.
  6. Upgrade notes and checksums.
  7. What’s next, in the same three horizons as the status page, and what happened to the last note’s “next” items.
