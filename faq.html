01Topic one6 questions

Getting started.

Can we try it?

Yes, and Validate is the easiest place to start. It isn’t a download yet, because we’re still finishing licensing. It will use signed licence files that work offline, so nothing has to call home. Until then, book a release check and we’ll run Validate with you on a model server you already have. Trials are coming.

Core and Serve are open source (Apache-2.0) and public on GitHub (github.com/fusezap/fusezap-core). We can also run them with you, on your hardware or in your environment.

What’s open source and what’s licensed?

FuseZap Core and Serve are open source (Apache-2.0) and public on GitHub (github.com/fusezap/fusezap-core). Core is the engine that runs models on a chip, and Serve is the OpenAI-compatible server on top of it. Anyone can run them and port them to a new chip.

FuseZap Validate is our licensed product. It checks each release of a model server against a full-precision reference and the release you approved last time, then says PROMOTE, BLOCK or REVIEW and shows the evidence. It works with any OpenAI-compatible server, so you can use it whether or not you run Core. So far we’ve run it on vLLM, SGLang, TensorRT-LLM, TGI, a hosted API (Fireworks) and FuseZap. Early access is open now, and trials are coming.

Why not just use Ollama?

If you want to run an open model on your own laptop or a single GPU, for yourself, use Ollama or LM Studio. They’re built for running models locally, usually quantized, for one person or a small team. They’re the right tool for that, and we’d recommend them.

FuseZap does a different job, for chip makers and platform teams. They need to bring up and qualify models on new hardware. They need to serve many people at once on a cluster, across several GPUs, without having to quantize, and prove the answers are accurate against a full-precision reference. Their users expect an OpenAI-compatible API with tool calls and structured output. And before each release goes out, they need evidence that it’s safe. That’s what Validate gives them.

Which chips does FuseZap run on?

Today: NVIDIA GPUs, Apple silicon, ordinary CPUs and AWS Inferentia2, where FuseZap serves a 7B model across both cores of one chip. One image model, FLUX.2 [klein], also runs on Inferentia2 and on AWS Trainium1: correct, not fast yet. We’re exploring AMD next. Model by model, it’s all in the matrix.

How long does it take to get a model running?

It depends on how mature your toolchain is. We aim for weeks to a first model, not quarters. After a first call, we can give you an honest estimate.

How fast do you support a new model?

That depends on what’s new about it. A new release in a family we already support, like a new Qwen version, is usually new weights on a familiar design. We aim to have one of those running and qualified within days.

A genuinely new design, such as a new kind of attention or a mixture-of-experts model, takes longer, because the compiler may need new building blocks. We’ll publish real turnaround times as we collect them, and the response times we agree go into your contract.

02Topic two3 questions

Working together.

Do you replace our compiler or runtime?

Partly, so here’s exactly which part. We use your low-level toolchain and driver to compile and launch kernels, and we call any tuned kernels you already have. We replace the layers above them: fusion, scheduling, kernel generation and serving. Anything that touches your silicon directly stays yours.

vLLM says it runs any model on any hardware. Why FuseZap?

We like vLLM. It’s an excellent serving engine, and on NVIDIA we’ve only just caught up with it. On one H100 with a 7B model, back to back on the same machine, FuseZap is now level with vLLM. On 70B models split across two H200s we’re within 5% of its per-token speed, but vLLM is still quicker to the first token.

Its hardware support is real too. But each chip in the vLLM world sits on its maker’s own work underneath: PyTorch or JAX support for the operations models use, and hand-tuned kernels for attention, matrix multiply and each new model feature. That work takes a chip team months.

FuseZap works one level lower. Models break down into 28 basic operations, and we generate the code for your chip from those. So you bring a kernel compiler and a driver rather than a whole framework port. The few operations that decide speed, like matrix multiply and attention, still get tuned kernels, yours or ours. Then Validate re-checks every model when anything changes. A serving engine doesn’t do that part.

You don’t have to choose. You can keep vLLM for serving and use Validate to check it. We also believe a second model on a new chip costs far less than the first. We’re measuring that on Inferentia2 now, and we’ll publish the number whichever way it comes out.

Is it ready for production?

FuseZap Validate is built for exactly that: qualifying production model-server releases, and we run it with design partners today. FuseZap Core & Serve isn’t ready for a large fleet yet, and we’d rather say so. Right now we’re focused on getting models running correctly on new chips.

FuseZap exposes Prometheus metrics with vLLM’s metric names, so the dashboards you already have will work. Tracing and access control come from standard tools you probably run already, such as OpenTelemetry and an API gateway. The rest, like rollouts and failure recovery, we’ll build with our first design partners. The engineering notes list what exists today.

03Topic three7 questions

Ownership, trust and cost.

Who owns the code for our chip?

You do. The code we write for your chip is yours. We can hand it over in full, with its tests, so your team can run it without us.

How do you protect our IP?

We work under NDA, on your hardware or in your environment if you prefer. Nothing about your chip goes into work we do for anyone else.

What if FuseZap goes away?

You won’t be stranded. The code written for your chip is yours. FuseZap Core and Serve are open source (Apache-2.0) and already public on GitHub.

Validate, our licensed product, is covered by source-code escrow. If FuseZap ever goes out of business, an independent escrow agent releases its source to you, so you can keep checking your own releases. The exact terms are in your contract.

Who do we call when something goes wrong?

Promod Gangadharan, our CEO. Promod is accountable for your delivery and is your named contact for anything that needs escalating. Support runs 8am to 5pm Pacific, Monday to Friday.

Does FuseZap use AI, or send our data to an AI service?

The product doesn’t. FuseZap Core, the serving engine and Validate run entirely on your systems and never call an AI service.

Our engineers do use AI coding tools in their work. When that work touches your confidential material, your contract sets the rules. We only use providers that don’t train on your data, and we name them up front. You can mark anything off-limits, or have the tools run in your own environment.

Are there royalties? Does FuseZap send data back to you?

No per-device royalties. You pay to bring your chip up, and then a subscription to keep models qualified, however many chips you ship.

FuseZap doesn’t send usage data, model data or anything else back to us. It runs entirely in your environment. Downloading a public model talks to Hugging Face, not to us, and you can point FuseZap at local copies instead.

What does it cost?

The assessment is free. Working together starts with a 90-day pilot, paid in four stages tied to results we agree up front. You only pay for the stages you start, and you can stop at any gate.

If you carry on, the pilot fee counts toward your first year, which is a yearly subscription to keep every model qualified, however many chips you ship. Our first design partners get a lower pilot price in return for being a reference.

Nothing matches that yet. That’s a good question to ask us directly.
